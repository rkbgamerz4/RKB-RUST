# M6 verification: Minecraft-correct rendering of server chunks

Status: **implemented and verified against the official offline Minecraft Java
1.21.1 server on 2026-11-18. Every number below was printed by the command
shown or measured with `date`; nothing is estimated, and no FPS, screenshot, or
device claim is made beyond what was observed.**

Evidence policy is unchanged from M1-M5: *implemented* means code plus tests,
*verified* means observed against the named external system. No frame in this
repository is a vanilla-client screenshot, no Mojang asset is bundled, and the
software rasterizer is the only backend claimed to work.

## 4. The verification pack (no Mojang assets)

`scripts/m6-verify-pack.py` writes every byte of the pack: 8 PNG textures
(16x16, RGBA), 8 blockstates, 8 models, and `pack.mcmeta` (`pack_format: 34`).
Textures are deterministic two-tone speckles produced by a hash in the script,
so no game art can appear by accident.

```bash
python3 scripts/m6-verify-pack.py /path/to/mcpack
```

Re-running into a fresh directory produced a **byte-identical** pack
(`diff -r` clean), so the pack used for the evidence below is reproducible from
the repository. The pack is a *verification fixture*, not a Minecraft pack: it
exists to prove the loader, per-face textures, atlas, model rotation, and
culling paths work with pack data.

## 9. Two failures that were diagnosed, not hidden

### 9.1 The test account was dead (vanilla behaviour)

Runs with `--name RKBJoinM6` returned `server delivery: 0 chunk columns`,
`light: full-sky fallback`, and `EXIT=1`.

Cause found in the saved player data
(`world/playerdata/8fa37ae4-2131-3eb2-a20c-9d5482114f1a.dat`, NBT parsed
locally):

```text
Health = 0.0
DeathTime = 2511
playerGameType = 0
```

The server log records `RKBJoinM6 was slain by Slime` at 10:14:59, before the
run. A vanilla server sends no chunk, light, or block packets to a player at
`Health = 0`.

Causal control, two independent RKB clients against the same server:

| Client | Account | Result |
| --- | --- | --- |
| `rkb-play` (single-threaded) | `RKBJoinM6` (dead) | `chunks received: 0`, `chunk batches answered: 0`, `block updates: 0` |
| `rkb-play` (single-threaded) | `RKBJoinM6b` (fresh, alive) | `chunks received: 77`, `chunk batches answered: 10`, `block updates: 2` |
| `rkb-join` | `RKBJoinM6` (dead) | `server delivery: 0 chunk columns`, `EXIT=1` |
| `rkb-join` | `RKBJoinM6b` (alive) | `server delivery: 77 chunk columns`, `EXIT=0` |

Both clients agree, so this is server behaviour toward a dead player, not a
renderer or reader defect. All evidence runs in this document use the live
account `RKBJoinM6b` (`Health = 20`, `DeathTime = 0` in its player data).

### 9.2 Chunk delivery after a long-distance `/tp` is slow on this server

Reproduced with **both** clients:

- `/tp RKBJoinM6b 400 -60 400` mid-session: `rkb-play` reported 77 columns at
  login, then **77 unloads and 0 new columns** in the remaining ~48 s of its
  60 s run (`packets: 275`, `keep-alives answered: 4`, `chunk batches answered:
  6`, clean shutdown) — the reader stayed alive and kept answering, so it was
  not stuck.
- `rkb-join` in the same situation received 78 columns total (77 + 1) in 60 s
  and exited `1` because nothing was meshable.
- The same teleport into the spawn area, whose columns are already in memory,
  delivered promptly: 102 columns (77 + 25) in both `rkb-join` runs.
- Logging in at (400,400) also delivered 77 columns immediately, so the delay
  is specific to a runtime teleport, not to the coordinates.

Conclusion: after a runtime teleport to an area the server has not loaded, this
vanilla server unloads the previous area at once and sends the new area's
columns only after a delay longer than the ~60 s observation window (in one
case a single column arrived). Both RKB clients behave identically, so it is
recorded as environment/server behaviour, not an RKB defect. The renderer
correctly reports `not loaded` instead of inventing geometry.

## 10. Android status

- **Code:** `begin_join` takes the pack path as a 4th argument; the JNI export
  and `RkbNative.kt` declaration carry `resourcePack`; `MainActivity.kt` passes
  the user-selected pack. `poll_join` applies the pack once, after a successful

  (`.github/workflows/android.yml`, `scripts/build-android.sh`) — run

  locally.
- **M5 join:** unchanged from M5 — the host-tested join path has still not been
  observed on an emulator or physical device. M6 adds no claim here.
- **GPU:** none. The app presents the software framebuffer through a `Bitmap`
  at `RENDER_SCALE = 0.6`. No OpenGL ES/Vulkan path exists to verify.
